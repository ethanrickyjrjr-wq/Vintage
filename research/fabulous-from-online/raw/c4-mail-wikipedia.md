From Wikipedia, the free encyclopedia
URI scheme for linking email addresses
Not to be confused with [Malito](https://en.wikipedia.org/wiki/Malito "Malito").
**mailto** is a [Uniform Resource Identifier](https://en.wikipedia.org/wiki/Uniform_Resource_Identifier "Uniform Resource Identifier") (URI) scheme for [email](https://en.wikipedia.org/wiki/Email "Email") resources. More specifically, mailto URIs identify resources reachable via network mail, thus a mailto URI designates one or more _mailboxs_ via use of [email addresses](https://en.wikipedia.org/wiki/Email_address "Email address").[[1]](https://en.wikipedia.org/wiki/Mailto#cite_note-rfc6068-1) Clicking on a mailto link opens an email client in compose mode, typically with one or more pre-filled form fields.
A common use is to produce [hyperlinks](https://en.wikipedia.org/wiki/Hyperlink "Hyperlink") on [websites](https://en.wikipedia.org/wiki/Websites "Websites") that allow users to send an [email](https://en.wikipedia.org/wiki/Email "Email") to a specific address directly from an [HTML](https://en.wikipedia.org/wiki/HTML "HTML") document, without having to copy and enter it into an [email client](https://en.wikipedia.org/wiki/Email_client "Email client"). 
## History
[[edit](https://en.wikipedia.org/w/index.php?title=Mailto&action=edit&section=1 "Edit section: History")]
This scheme is formally described in [RFCs](https://en.wikipedia.org/wiki/Request_for_Comments "Request for Comments") published by the [IETF](https://en.wikipedia.org/wiki/IETF "IETF"). It was first introduced in RFC 1630, published in June 1994, which sought to establish the concept of URIs.[[2]](https://en.wikipedia.org/wiki/Mailto#cite_note-2) It was then detailed in RFC 1730, published in December 1994, which derived the concept of URLs from RFC 1630.[[3]](https://en.wikipedia.org/wiki/Mailto#cite_note-3) This detail amounted to the scheme simply referencing nothing more than an email address. As discussed later in RFC 2368, published in July 1998, mailto URLs were unusual since resolution did not result in an immediate retrieval of a resource, but rather initiated the creation of an email, which the user could further edit, before optional transmission. This new RFC sought to enhance functionality, allowing for multiple email addresses to be specified using commas, and allowing email header and body content to be specified using the URI [query string](https://en.wikipedia.org/wiki/Query_string "Query string") component (utilising a `key=value` form with an [ampersand](https://en.wikipedia.org/wiki/Ampersand "Ampersand") (`&`) [delimiter](https://en.wikipedia.org/wiki/Delimiter "Delimiter")), which would thus expand the set of data pre-populated in the new email.[[4]](https://en.wikipedia.org/wiki/Mailto#cite_note-4) The mailto scheme remains recognised by the current internet standard for URIs, RFC 3986, published in January 2005.[[5]](https://en.wikipedia.org/wiki/Mailto#cite_note-5) RFC 6068, published in October 2010, supplanted RFC 2368 with refinements.[[1]](https://en.wikipedia.org/wiki/Mailto#cite_note-rfc6068-1)
## Syntax
[[edit](https://en.wikipedia.org/w/index.php?title=Mailto&action=edit&section=2 "Edit section: Syntax")]
Mailto URIs are composed of the scheme `mailto:` and zero, one, or more recipient addresses separated with a comma. Additionally, email headers such as `cc` or `subject` can be added as [attribute-value pairs](https://en.wikipedia.org/wiki/Attribute-value_pairs "Attribute-value pairs") in the [query component](https://en.wikipedia.org/wiki/Query_string "Query string") of the URI.
[Percent-encoding](https://en.wikipedia.org/wiki/Percent-encoding "Percent-encoding") must be used for the local-part of the Email addresses and for the header values. The Domain parts of the addresses can also be encoded using percent-encoding but using [IDNA-Encoding](https://en.wikipedia.org/wiki/Internationalized_domain_name "Internationalized domain name") is recommended for interoperability with legacy software.[[1]](https://en.wikipedia.org/wiki/Mailto#cite_note-rfc6068-1)
## Examples
[[edit](https://en.wikipedia.org/w/index.php?title=Mailto&action=edit&section=3 "Edit section: Examples")]
"mailto" can be used within an [HTML](https://en.wikipedia.org/wiki/HTML "HTML") document to generate a link for sending email:

```
<a href="mailto:someone@example.com">Send email</a>

```

Clicking on the hyperlink automatically opens the default email client, ready to compose a new email, with the destination email address pre-filled.
It is possible to specify initial values for headers (e.g. subject, cc, etc.) and message body in the URL. Blanks, carriage returns, and line feeds cannot be directly embedded but must be [percent-encoded](https://en.wikipedia.org/wiki/Percent-encoding "Percent-encoding"):[[6]](https://en.wikipedia.org/wiki/Mailto#cite_note-6)

```
<a href="mailto:someone@example.com?subject=This%20is%20the%20subject&cc=someone_else@example.com&body=This%20is%20the%20body">Send email</a>

```

Multiple addresses can be specified:[[1]](https://en.wikipedia.org/wiki/Mailto#cite_note-rfc6068-1)

```
<a href="mailto:someone@example.com,someoneelse@example.com">Send email</a>

```

The to-address can also be omitted:

```
<a href="mailto:?subject=mailto%20with%20examples&body=https%3A%2F%2Fen.wikipedia.org%2Fwiki%2FMailto">Share this knowledge...</a>

```

Only the initial header should be prepended with a [question mark](https://en.wikipedia.org/wiki/Question_mark "Question mark"). All subsequent headers require an [ampersand](https://en.wikipedia.org/wiki/Ampersand "Ampersand"). If this convention is not followed, mail clients will not properly copy over the headers to the new email.[[1]](https://en.wikipedia.org/wiki/Mailto#cite_note-rfc6068-1):§6.1
## Security and privacy
[[edit](https://en.wikipedia.org/w/index.php?title=Mailto&action=edit&section=4 "Edit section: Security and privacy")]
A number of security issues are mentioned in RFC 6068,[[1]](https://en.wikipedia.org/wiki/Mailto#cite_note-rfc6068-1):§7 one of them being robotic [address harvesting](https://en.wikipedia.org/wiki/Address_harvesting "Address harvesting"). Mailto constructs are locatable within HTML pages by automated means which typically include the use of [DOM](https://en.wikipedia.org/wiki/Document_Object_Model "Document Object Model") constructs or [regular expressions](https://en.wikipedia.org/wiki/Regular_expression "Regular expression"). Addresses harvested by such means are liable to be added to [spammers](https://en.wikipedia.org/wiki/E-mail_spam "E-mail spam")' mass-mailing lists and thus to receive large amounts of unwanted mail.
While methods exist to "harden" mailto links against harvesting—[address munging](https://en.wikipedia.org/wiki/Address_munging "Address munging") and [JavaScript](https://en.wikipedia.org/wiki/JavaScript "JavaScript")-based address [obfuscation](https://en.wikipedia.org/wiki/Obfuscation_\(software\) "Obfuscation \(software\)") among them—these protections can be circumvented by sufficiently sophisticated harvesting robots. Other techniques, like walling the address behind a [CAPTCHA](https://en.wikipedia.org/wiki/CAPTCHA "CAPTCHA") or similar "humanity check", provide security on par with that available for other contact methods, most notably [web forms](https://en.wikipedia.org/wiki/Form_\(HTML\) "Form \(HTML\)"), which experience similar challenges with preventing spam.
